1. Mental Model — The Feature in One Picture

Think of the gallery as a slideshow player with a detail inspector that opens as a modal.

  • Gallery (background): Full-bleed preview image, thumbnail strip at bottom, overlay controls (prev/next/play-pause/info toggles).
  • Modal (foreground): A dialog that opens on top with the same image, metadata, like button, share-to-clipboard, and its own prev/next chevrons.
  • URL state: The ?image=filename query param deep-links to a specific image. Change it via browser back/forward and the modal syncs.
  • Controller: A useReducer-based hook owns all state transitions so no two components disagree about what's open.

3. Data Model & Types

GalleryImage

interface GalleryImage { filename: string // e.g. "photo-1.jpg" src: string // "/documentary_portfolio/photo-1.jpg" alt: string // fallback = caption or filename year: string caption?: string organization?: string camera?: string // EXIF lens?: string exposure?: string focalLength?: string iso?: string }

Built in imageList.ts from filesystem scan + metadata.json lookup.

Controller State

interface DocumentaryGalleryState { currentIndex: number // gallery cursor position direction: number // -1 | 0 | 1 (animation dir) isSlideShowPlaying: boolean // autoplay on/off modalPhase: "closed" // lifecycle state machine | "open" | "closing" selectedImageId: string | null // which image in modal (or null) wasSlideShowPlaying: boolean // saved for restore on close }
Critical invariant: currentIndex is the gallery cursor. selectedImageId is the modal subject. When the modal is open, they point to the same image. When the modal closes, selectedImageId goes null but currentIndex stays — the gallery continues from where you left off.
Why direction exists: Framer Motion needs a custom prop to know whether to animate left-to-right (direction=1) or right-to-left (direction=-1). Direction=0 means "no slide animation" — used on initial mount and URL-sync opens.

4. State Architecture & Reducer Pattern

The feature uses useReducer instead of multiple useState calls. This is deliberate: a reducer guarantees that state transitions are atomic, predictable, and testable without rendering a component.

Action Types

Action When it fires State changes
OPENUser clicks "Get a Print" or thumbnail to open modalmodalPhase="open", sets selectedImageId, pauses slideshow
REQUEST_CLOSEUser clicks overlay, Escape, or close buttonmodalPhase="closing"
CLOSE_COMPLETEDialog animation finishes (onAnimationEnd)modalPhase="closed", clears selectedImageId, restores slideshow
GO_NEXTSlideshow interval or gallery next arrowcurrentIndex++, wraps, direction=1
GO_PREVGallery prev arrowcurrentIndex--, wraps, direction=-1
MODAL_NEXTModal chevron right or ArrowRight while modal openSame as GO_NEXT + updates selectedImageId
MODAL_PREVModal chevron left or ArrowLeft while modal openSame as GO_PREV + updates selectedImageId
SELECT_INDEXThumbnail strip clickcurrentIndex = action.index
TOGGLE_SLIDESHOWPlay/Pause buttonFlips isSlideShowPlaying
SYNC_FROM_ROUTEURL searchParams changeOpens/closes modal based on ?image= param

Why useReducer vs useState?

CriterionuseStateuseReducer
Multiple interdependent fieldsRisk of stale closures, missed updatesOne dispatch, one atomic transition
TestabilityNeed to render componentPure function: reducer(state, action) → state
Complexity scalingBecomes spaghetti beyond 3-4 statesNew action = new case. Scales linearly.
DebuggingHard to log state transitionsEasy to log every dispatch + before/after
// Pure function — testable without React function documentaryGalleryReducer( state: DocumentaryGalleryState, action: DocumentaryGalleryAction ): DocumentaryGalleryState { switch (action.type) { case "OPEN": return { ...state, currentIndex: action.index, modalPhase: "open", selectedImageId: action.imageId, wasSlideShowPlaying: state.isSlideShowPlaying, // save for restore isSlideShowPlaying: false, // pause }; case "CLOSE_COMPLETE": if (state.modalPhase !== "closing") return state; // guard return { ...state, modalPhase: "closed", selectedImageId: null, isSlideShowPlaying: state.wasSlideShowPlaying, // restore }; // ... more cases } }
Guard pattern: Notice how CLOSE_COMPLETE checks state.modalPhase !== "closing" and returns early. This is called a state-machine guard. It prevents a close animation from completing twice, or from completing before the close was ever requested. Every action that only makes sense in a specific phase should have a guard.

5. URL Synchronization (Deep Linking)

The gallery uses the URL ?image=filename as a shared source of truth between the controller (internal state) and the browser (external navigation).

The Two Hooks Pattern

Rather than putting URL logic inside the controller, the code splits it into two hooks that communicate via a bridge pattern:

useGalleryRouteState.ts ─── reads: useSearchParams() ─── writes: router.replace() ─── exposes: { selectedImageId, setSelectedImageId }

This hook is the I/O boundary. It talks to Next.js router. It knows nothing about modals, slideshows, or state machines.

useDocumentaryGalleryController.ts ─── reads: routeImageId (prop) ─── writes: setRouteImageId (prop) ─── owns: reducer, slideshow, modal lifecycle

This hook is the state engine. It receives URL state as a prop (dependency injection via the parent). It calls setRouteImageId when modal state changes.

Bidirectional Sync Flow

State → URL (controller writes)

useEffect [modalPhase, selectedImageId]:
  desiredImageId = modalPhase === "open"
    ? selectedImageId
    : null

  if (desiredImageId !== routeImageId):
    setRouteImageId(desiredImageId) // triggers router.replace

URL → State (controller reads)

useEffect [routeImageId]:
  dispatch({
    type: "SYNC_FROM_ROUTE",
    imageId: routeImageId,
    index: routeImageId
      ? imageIndexById.get(routeImageId)
      : null
  })

SYNC_FROM_ROUTE reducer:
  • imageId=null, modalPhase="open" → start closing
  • imageId=null, modalPhase≠"open" → no-op
  • index=null → no-op (bad URL)
  • same as current → no-op
  • valid → open modal at that image
Why this matters for deeply-linked sharing: A user can share a URL like /documentary-portfolio?image=photo-1.jpg. A friend who opens it will see the modal open on that exact image. The initial state is computed via getInitialStateFromRoute() which reads routeImageId before the first render.
Architectural risk: The URL sync uses a useEffect, which means there's a one-tick delay between "user opens modal" and "URL updates". The guard pendingOpenRef (documented in ARCHITECTURE.md) prevents the URL-update effect from re-triggering itself. In this implementation, the guard is handled implicitly: the controller writes to setRouteImageId, which triggers router.replace, which updates searchParams, which re-runs the SYNC_FROM_ROUTE effect — but by then the state is already in sync, so the reducer's early-return guard prevents loops.

Flow D: Close Modal (3-Phase)

Phase 1: REQUEST_CLOSE └─ Trigger: overlay click / Escape / X button └─ dispatch(REQUEST_CLOSE) └─ modalPhase = "closing" └─ effect: isDialogOpen = false (since isDialogOpen is derived: modalPhase === "open") Phase 2: Dialog animates closed └─ Radix DialogContent plays exit animation └─ shouldRenderModalContent = true (modalPhase !== "closed") → content stays mounted during animation Phase 3: CLOSE_COMPLETE └─ onAnimationEnd fires on DialogContent └─ guards: ├─ modalPhase === "closing" (yes) ├─ event.target === event.currentTarget └─ data-state === "closed" └─ dispatch(CLOSE_COMPLETE) └─ Reducer: ├─ modalPhase = "closed" ├─ selectedImageId = null └─ isSlideShowPlaying = wasSlideShowPlaying (restore) └─ URL sync: desiredImageId = null → setRouteImageId(null) → router.replace("/documentary-portfolio") // clears ?image=
Risk: The CLOSE_COMPLETE depends on onAnimationEnd. If the animation doesn't fire (e.g., Radix DialogContent changes its CSS, or a parent AnimatePresence interferes), the controller gets stuck in "closing". A timeout fallback would make this more robust.

7. Keyboard Navigation System

The keyboard handler lives in DocumentaryGallery.tsx as a single useEffect with window.addEventListener("keydown", handler).

useEffect(() => { const handler = (event: KeyboardEvent) => { // GUARD: Don't steal focus from form elements if ( event.target instanceof HTMLInputElement || event.target instanceof HTMLTextAreaElement || event.target instanceof HTMLSelectElement ) { return; } if (event.key === "ArrowLeft") { if (isDialogOpen) { goPrevInModal(); return; } if (canInteractWithGallery) goPrev(); return; } if (event.key === "ArrowRight") { if (isDialogOpen) { goNextInModal(); return; } if (canInteractWithGallery) goNext(); } }; window.addEventListener("keydown", handler); return () => window.removeEventListener("keydown", handler); }, [canInteractWithGallery, goNext, goNextInModal, goPrev, goPrevInModal, isDialogOpen]);

Decision Tree

KeyPress ├─ Is focus in input/textarea/select? → IGNORE (guard) ├─ ArrowLeft │ ├─ isDialogOpen? → goPrevInModal() │ └─ canInteractWithGallery? → goPrev() └─ ArrowRight ├─ isDialogOpen? → goNextInModal() └─ canInteractWithGallery? → goNext()
Why this is correct: When the modal is open, left/right navigate in the modal. When closed, they navigate the gallery. Escape is handled natively by Radix Dialog (no competing handler). The form-element guard prevents arrow keys from interfering with typing in comment inputs.
Dependency array note: The effect re-registers the listener whenever canInteractWithGallery or isDialogOpen changes. This is necessary because the handler captures these values from the closure. An alternative would be using a ref, but the current approach is simpler. The cost is slight: re-registering the listener on every modal open/close.

8. Modal Lifecycle (3-Phase Close)

The modal uses a 3-phase state machine to handle the fact that Radix Dialog animations are CSS-driven and asynchronous. The problem: if you set open=false and immediately unmount the content, the exit animation never plays.

The Three Phases

PhaseisDialogOpenshouldRenderModalContentselectedImageIdMeaning
"closed" false false null No modal. Gallery is interactive.
"open" true true "filename" Modal visible. Gallery controls disabled.
"closing" false true (content still mounted!) "filename" Dialog shell animates out. Content stays for teardown.

Why 3 phases instead of 2?

A 2-phase approach (open/closed) would force you to either:

  • Unmount content immediately — exit animation never plays; content disappears abruptly.
  • Delay unmounting with a setTimeout — race conditions, magic numbers, fragile.

The 3-phase approach uses Radix's own onAnimationEnd callback, so the only delay is the actual CSS animation duration. No magic numbers, no race conditions.

DialogContent onAnimationEnd: └─ modalPhase === "closing" ? └─ event.target === event.currentTarget ? └─ data-state === "closed" ? └─ dispatch(CLOSE_COMPLETE) └─ modalPhase = "closed" └─ selectedImageId = null └─ restore slideshow Without these guards: ├─ onAnimationEnd fires for CHILD animations too │ (event.target === event.currentTarget fixes this) ├─ Could fire during OPEN animation │ (data-state === "closed" fixes this) └─ Could fire twice if component re-renders (modalPhase !== "closing" guard fixes this)

9. Slideshow Engine

The slideshow is a single setInterval that fires goNext every SLIDE_SHOW_INTERVAL (5000ms). It's managed entirely inside the controller hook.

useEffect(() => { if (!state.isSlideShowPlaying || images.length === 0) { return; } const interval = setInterval(goNext, slideShowInterval); return () => clearInterval(interval); }, [goNext, images.length, slideShowInterval, state.isSlideShowPlaying]);

Transient State Save/Restore

When the modal opens, the slideshow must pause. When the modal closes, it should resume if it was playing before. This is the Transient State Save/Restore pattern.

Save on open

case "OPEN": return { ...state, wasSlideShowPlaying: state.isSlideShowPlaying, isSlideShowPlaying: false, }; // Capture the CURRENT playing state // BEFORE setting it to false. // If it was already false, that's fine: // wasSlideShowPlaying = false.

Restore on close

case "CLOSE_COMPLETE": return { ...state, modalPhase: "closed", selectedImageId: null, isSlideShowPlaying: state.wasSlideShowPlaying, }; // If wasSlideShowPlaying was true → resume // If wasSlideShowPlaying was false → stay paused // Always set wasSlideShowPlaying aside: // no branching needed.
Why a ref isn't needed here: The ARCHITECTURE.md says to use a ref for transient state. But the reducer handles it naturally: wasSlideShowPlaying is part of the reducer state. The reducer captures the value at the moment of the OPEN dispatch (which is synchronous), so there's no stale closure issue.

10. Animation Patterns

The feature uses Framer Motion extensively for transitions. Here's every animation site and what it does.

Component Animation Trigger Key Prop
PreviewImage Full-bleed background crossfade with spring motion currentIndex changes (key prop) custom={direction}, spring stiffness=180
GalleryControls Left/right toolbars slide in from edges on mount Component mount initial={{ x: -20 }}, animate={{ x: 0 }}
InfoCard Blur-in, scale-in on tab change, layout animation id (tab) changes layout prop, AnimatePresence mode="wait"
IconButton Spring scale on hover/tap Hover, click whileHover={{ scale: 1.1 }}
ThumbnailStrip Slide up/down on idle timeout; scale on active thumbnail 4s idle timer, currentIndex change variants={{ visible, idle }}
ImageModal image Slide horizontal + blur transition on image change image.filename key changes custom={direction}, AnimatePresence mode="sync"
ImageModal metadata Fade + blur + slide-up on image change image.filename key changes initial={{ opacity: 0.65, y: 10, filter: "blur(2px)" }}
ImageModal share icon Crossfade between Share2 and Check icons shareCopied state toggle AnimatePresence mode="sync"
ImageLikeButton heart Rotate + slide on like/unlike toggle isLiked state change AnimatePresence mode="wait"
DialogContent CSS-driven fade + zoom-in/out Radix data-state attribute Tailwind: data-[state=open]:animate-in
The key prop trick: Framer Motion's AnimatePresence detects "new" vs "leaving" children by their key prop. When image.filename changes, the old element exits (plays exit animation) and the new element enters. This is why key={image.filename} on the motion.div is essential.
Performance note: AnimatePresence mode="sync" makes the old element exit and new element animate simultaneously. mode="wait" waits for exit to finish before entering. The image modal uses "sync" (snappier feel), while the info card uses "wait" (avoids overlapping text).

12. Reusable Architecture Patterns

These patterns are documented in ARCHITECTURE.md and exemplified in this feature. Learn them and you can build any modal-based UI.

PatternWhere UsedIn One Sentence
URL-Driven State useGalleryRouteState + controller URL sync Read state from URL on mount, write state to URL on change, sync bidirectionally with a guard to prevent loops.
Transient Save/Restore wasSlideShowPlaying in reducer Save a boolean before changing it, restore after the interrupting UI closes — no branching needed.
Controlled Dialog <Dialog open={isDialogOpen} onOpenChange={...}> Use open + onOpenChange props instead of DialogTrigger when the modal open is programmatic (not from a button near the dialog).
Disabled Prop Cascade canInteractWithGallery → GalleryControls → IconButton Pass a single disabled boolean through one level; each leaf checks it for both visual styling and click guarding.
Keyboard Guard Window keydown handler Early-return when focus is in an input/textarea/select to avoid stealing form interaction.
Layered Close Paths → Single Handler closeModal() / completeClose() Overlay click, Escape, close button, and URL clear all funnel into the same dispatch(REQUEST_CLOSE) → dispatch(CLOSE_COMPLETE) pipeline.
Fire-and-Forget UX Actions handleShare in ImageModal try/catch around clipboard API, toast on both success and failure, lock button during async operation.
State Machine Modal Lifecycle modalPhase: "closed" | "open" | "closing" 3 phases let the dialog exit animation play before unmounting content, with guards preventing duplicate transitions.

The Meta-Skill: Prompt Engineering for Code

Good prompts are:
  • Context-rich: Tell the agent about files, patterns, and conventions.
  • Specific: "Write a test" is vague. "Write a vitest test for the reducer's GO_NEXT action that verifies wrap-around from last index to 0" is precise.
  • Constrained: "Use the same pattern as X" or "Don't add new dependencies" or "Only modify files in src/app/(pages)/documentary-portfolio".
  • Iterative: Start broad, then narrow. "Read the controller file. Now I want to add an action. The reducer pattern uses switch/case. Can you add a RESET action?"
Prompt anti-patterns to avoid:
  • Doing it all at once: "Build the entire gallery feature" produces generic, pattern-broken code.
  • No context: "Write a reducer" without specifying state shape, actions, or conventions.
  • Ignoring errors: If an agent produces broken code, don't ask again — fix incrementally: "The type X doesn't exist, use Y instead."
